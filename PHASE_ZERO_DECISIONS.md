# Phase 0 decisions

The reproducible evidence is generated by `npm run evaluate` in
`artifacts/phase-zero-results.json`. These are prototype decisions, not
production-readiness claims.

## Decision summary

- **Nakama: CONDITIONAL-GO-FOR-LOAD-AND-RECOVERY-TESTS.** The real
  Nakama/PostgreSQL stack passed server-only tenant provisioning, forged tenant
  input, duplicate room-key isolation, cross-tenant room rejection, stale
  update rejection, host migration, tenant-scoped matchmaking, and an
  eight-player room at approximately 5 updates per second on the Singapore
  Railway/Supabase deployment. Restart recovery and sustained concurrent-game
  load are still required before private beta.
- **Creator-authored authoritative rules: NO-GO.** Deterministic replay,
  seeded randomness, fixed ticks, timeouts, memory limits, version pinning, and
  adapter failure containment work. The measured runner p95 exceeds the 10 ms
  target because every action starts a worker, and a Node worker executing
  restricted JavaScript is not a sufficient hostile-code boundary. Ship the
  host-authoritative room path first.
- **WebAssembly: NO-GO-FOR-MVP.** The 41-byte module starts quickly and runs
  deterministically, but this only validates a minimal integer ABI. State
  serialization, fuel metering, host capabilities, debugging, packaging, and
  agent authoring remain unresolved. Keep WebAssembly as a later runner format.

## Prototype outcomes

1. **Shared Nakama infrastructure — pass for deployed integration, conditional
   for private beta.** Compose and the runtime module are built, and tenant identity
   is held in server-only Nakama storage provisioned through the HTTP-key
   control-plane path. Real sessions and secure sockets against Railway Nakama
   and isolated Supabase PostgreSQL passed the isolation, room, migration,
   matchmaking, and bounded-load checks.
2. **Host-authoritative generic room — pass for local prototype.** Sixteen
   players, monotonic state, stale rejection, host migration, late joining,
   tenant rejection, and empty-room disposal are covered.
3. **Sandboxed browser hosting — pass for policy prototype.** Immutable
   per-game origins, opaque sandboxed iframes, restrictive headers, and
   deny-by-default outbound networking are generated. R2/CDN and browser escape
   tests still require a deployed target.
4. **Cross-language clients — pass for contract prototype.** JavaScript,
   Swift, Kotlin, and Unity expose the same Loki operations without leaking
   Nakama types. Native build and live transport conformance remain follow-up
   gates.
5. **Authoritative logic runner — fail.** Correctness and failure-containment
   checks pass, but latency and production isolation do not.
6. **Nakama-to-runner adapter — pass for local prototype.** Tenant checks,
   ordered actions, pinned rule versions, structured broadcasts, and continued
   operation after a broken match are covered.
7. **AI-assisted extraction — pass only for the bounded spike.** Four
   representative pure score rules produce equivalent Loki TypeScript and
   forbidden dependencies fail closed. This is not evidence for general game
   migration.
8. **WebAssembly spike — pass for execution, no-go for adoption.** Startup,
   deterministic execution, package size, and throughput are measured; the
   required production ABI and tooling are not.

## Reproduction

Run `npm install` and `npm run check`. Re-run the live stack with
`npm run validate:nakama`, then `npm run evaluate`; use
`npm run nakama:down` when finished. Next, add a sustained 16-player load and
stop/restart Nakama/PostgreSQL while active rooms reconnect before a full go
decision.
